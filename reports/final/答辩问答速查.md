# 轻量化混合 GraphRAG 答辩问答速查

## 1. 20 秒项目定义

本项目是一个面向 scikit-learn 6 个官方文档页面的轻量化 Knowledge-Graph-Enhanced RAG 问答 Agent。系统用规则 Router 选择文本、图或混合检索，用 Evidence Packer 组织可见证据，用本地 `qwen3:4b` 生成原子 Claim，再由确定性 Claim-level Verifier 决定保留、删除、部分回答、重试或拒答。重点贡献是证据控制、可审计运行和严格实验治理，不是基础模型创新。

## 2. 课题定位

### Q1：这是完整的 Microsoft GraphRAG 吗？

不是。准确表述是“基于预定义知识图谱的轻量化混合 RAG”或“Knowledge-Graph-Enhanced RAG”。项目借鉴图结构知识与文本证据结合的思想，但没有实现社区检测、社区摘要和全局检索流水线。

### Q2：项目的研究问题是什么？

核心问题有三个：图结构与文本证据能否形成可追溯回答；Verifier 能否控制无答案、错误前提和不受支持内容；Claim-level Partial-pass 能否缓解整题级验证造成的过度拒答。

### Q3：项目的主要创新点是什么？

不是提出新模型，而是在小型可控领域中，把预定义图关系、官方文本 Chunk、原子 Claim、逐字 quote、确定性验证、故障回退和冻结实验治理组合成一个可运行、可消融、可审计系统。

### Q4：为什么只覆盖 6 个官方页面？

短周期项目更需要可审核边界。6 页已经覆盖 6 类基础主题、180 个 Chunk、50 个实体和 100 条 approved 关系；固定范围使每条 Claim 能追溯到来源，也让无答案和拒答有明确含义。代价是不能泛化到完整 scikit-learn。

### Q5：为什么使用预定义图谱，不自动抽取？

预定义并审核关系能控制关系幻觉和数据噪声，适合六天科研实践。自动抽取会引入额外模型、审核成本和归因变量，不利于把研究重点放在检索、验证与拒答机制上。

## 3. 数据与检索

### Q6：知识库由什么组成？

6 个 scikit-learn 官方页面被切分为 180 个稳定 ID 的 Chunk；图谱包含 50 个实体和 100 条 approved 关系。文本证据使用 E ID，图路径使用 P ID，关系使用 R ID。

### Q7：数据运行时需要联网吗？

不需要。HTML 已缓存，Chunk、图数据和模型都在本地。没有网络时官方 URL 可能打不开，但本地检索和缓存证据仍可运行。

### Q8：当前文本检索是 Dense Retrieval 吗？

不是。当前正式文本检索主要是 TF-IDF 稀疏检索，不能把 Chroma 或 sentence-transformers 依赖直接表述成神经 Dense Retrieval 已进入主实验。Dense Retriever 只是在误差证明召回是主要瓶颈后才考虑的后续项。

### Q9：为什么同时使用文本和图？

文本提供定义、机制和逐字证据；图提供实体关系和多跳结构。混合检索把“结论是什么”和“原文如何支持”放在同一证据包中，比单独依赖任一层更容易审计。

### Q10：Evidence Packer 做什么？

它位于检索与 LLM 之间，完成去重、实体和标题匹配、题型配额、图路径绑定、条目与字符预算，并只把本次可见的 E、P、R ID 暴露给 LLM。对比题会平衡两个对象，多跳题会保留图绑定证据。

### Q11：为什么不直接提高 Top-K？

更高 Top-K 会增加噪声和上下文长度，不保证关键证据更突出。Packer 用问题类型和实体覆盖组织证据，只有 0 条 Claim 可保留时才把 Top-K 从 8 扩到 16 并执行一次 Hybrid retry。

### Q12：图后端为什么使用 NetworkX，不是 Neo4j？

两者实现同一个 `GraphRepository` 接口。NetworkX 完全本地、部署简单，是正式实验默认后端；Neo4j 适配代码存在，但当前没有完成服务部署和正式性能基准，所以不能声称 Neo4j 已验证优于 NetworkX。

## 4. Router、LLM 与工作流

### Q13：为什么 Router 使用规则？

规则 Router 在固定领域更稳定、可解释。`qwen3:4b` 的 QueryPlan 探针 20/20 能生成合法 Schema，但只有 1/20 语义正确，因此 LLM Planner 会降低路由质量，没有进入主链路。

### Q14：LLM 在系统里负责什么？

LLM 只在 answer 节点把已选证据组织成最多 4 条原子 Claim，不负责规划、实体链接或检索。最终正文也不是直接信任自由文本，而是由通过程序校验的结构化 Claim 重建。

### Q15：为什么选择 `qwen3:4b`？

它可以本地部署，资源规模适合当前机器，并支持 JSON Schema 结构化输出。项目没有做多模型公平对比，因此只能说它满足当前工程约束，不能说它是最佳模型。

### Q16：LangGraph 的作用是什么？

LangGraph 编排 route、retrieve、pack、answer、verify、retry 和 finalize 状态转移，并让每次调用的 trace 可追踪。未安装 LangGraph 时有等价本地状态机兼容路径；当前环境实际使用 LangGraph。

### Q17：LLM 服务失败怎么办？

只捕获预期的不可用、超时、空响应或结构化失败，并显式回退到确定性规则生成器。界面同时显示 requested backend、actual backend、fallback 和原因，不会把 fallback 伪装成 LLM 输出。

## 5. Claim-level Verifier

### Q18：什么是原子 Claim？

一条 Claim 只表达一个可独立验证的专业事实，不能用“并且”“同时”“因此”把多个结论绑在一起。每条 Claim 必须给出可见 E/P/R ID 和对应逐字 quote，最多生成 4 条。

### Q19：Verifier 检查什么？

它检查引用 ID 是否存在、quote 是否为证据原文子串、术语与问题限定是否覆盖、图路径和关系是否有效、错误前提是否成立，以及回答是否真正响应问题动作。每条 Claim 产生独立的保留或删除结果。

### Q20：`PASS`、`PARTIAL_PASS`、`RETRY`、`REFUSE` 如何区分？

- `PASS`：应回答的 Claim 都得到支持；
- `PARTIAL_PASS`：至少一条 Claim 得到支持，另一部分被删除并披露证据不足；
- `RETRY`：当前 0 条 Claim 可保留，但仍允许扩大 Hybrid 检索一次；
- `REFUSE`：重试后仍无可保留 Claim，或问题前提被判为错误。

### Q21：Partial-pass 为什么能缓解过度拒答？

旧 strict 策略是一条 Claim 不支持就整题拒答。Partial-pass 分别验证并只用 retained Claims 重建答案，因此有证据的部分不会和不支持部分一起丢失，被删除内容也不会泄漏到正文。

### Q22：为什么“随机森林为什么更稳定”以前会拒答？

历史 strict 版本把多个机制事实放在同一回答中，只要其中一条 quote 或术语覆盖不足，就整体拒绝。Claim-level 版本会保留被直接支持的部分。2026-07-25 的真实 LLM smoke 对“随机森林降低方差的机制是什么”返回 `PARTIAL_PASS`，保留 3/4 Claim；这只证明当前运行路径可用，不是新的正式实验。

### Q23：Partial-pass 会不会留下半句话或语义破碎？

不会直接删除自由文本片段。系统按保留 Claim 重新构造最终正文，并附加未覆盖部分的证据不足说明，因此过滤发生在结构化事实层。

### Q24：如何防止 Prompt Injection？

Prompt 明确把问题和证据中的指令只当数据；LLM 只能使用当前证据包；程序限制可引用 ID、检查逐字 quote，并由结构化 Claim 重建正文。该设计降低风险，但不能声称覆盖所有攻击方式。

### Q25：观察 hallucination 为 0 是否表示绝对不会编造？

不是。`0/16` 只表示 Partial-pass 在 extension 的 16 条实质答案中没有被本次评分观察到 hallucination。样本小、只有单一用户确认，不能外推为绝对零风险。

## 6. 实验设计与治理

### Q26：dev、pilot、final、extension 如何划分？

10 道 dev 用于调试；40 道 pilot 用于一次冻结前回归；v1 的 40 道 final 是历史规则基线冻结结果；v2 extension 有 23 题、4 方法和 92 次调用，只执行一次。8 道 demo 只用于展示，不进入正式指标。

### Q27：为什么不能重跑 final、pilot 或 extension？

这些题的结果已经被观察。再根据逐题结果改参数或选择运行，会造成测试泄漏。项目用 release、execution state、receipt、文件哈希和脚本校验保护一次性执行状态。

### Q28：四种 extension 方法分别是什么？

Rule Baseline 使用规则生成；LLM Strict 使用整题级严格验证；LLM No Verifier 记录 shadow 验证但不干预答案；LLM Partial-pass 使用逐 Claim 保留。四种方法都固定 Rule Router，三个 LLM 方法共用 Retriever、Packer、Prompt、模型和生成参数。

### Q29：盲评如何进行？

23 题乘 4 方法形成 92 行匿名 A/B/C/D 答案，评分时不暴露方法 ID 和 expected 字段。Codex 辅助初评后由用户逐行审核确认，评分锁定后才读取独立 method key 解盲。

### Q30：这是双人独立标注吗？

不是。准确表述是“Codex 辅助评分，经单一用户审核确认”。它降低了方法身份偏差，但不能替代双人独立标注和一致性分析。

### Q31：为什么不同指标的分母不一样？

Correctness 对全部 23 题评分；Faithfulness、Hallucination 和 Readability 只对实质答案评价，拒答不进入这些分母；Over-refusal 只看 19 道可回答题。因此必须同时报告比例和 `n`，不能只比较小数。

### Q32：自动 Decision Accuracy 等于人工 Correctness 吗？

不等于。自动指标只判断 answer/refuse 决策是否符合预期；人工 Correctness 评价答案内容覆盖和正确程度。v1 的 39/40 也是决策准确率，不能与 extension 人工 Correctness 直接比较。

### Q33：样本是否足以证明统计显著性？

不足。Extension 只有 23 题，各题型约 2～4 题，并且只有单一用户确认。当前结果用于描述性比较、机制验证和误差定位，不主张统计显著性或广泛泛化。

## 7. 结果解释

### Q34：v1 规则基线结果如何？

冻结的 40 题 final 上 Decision Accuracy 为 39/40，4/4 无答案题正确拒答，平均本地工作流耗时 1.48 毫秒。唯一错误是 AdaBoost 定义题被保守拒答；该版本不包含 LLM。

### Q35：Extension 的四方法核心结果是什么？

| 方法 | Correctness | Faithfulness | Hallucination | Over-refusal | Readability | Mean E2E |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Rule Baseline | 0.5870 | 0.8810 (n=21) | 0/21 | 0/19 | 3.56 (n=18) | 5.46 ms |
| LLM Strict v2 | 0.3043 | 1.0000 (n=3) | 0/3 | 16/19 | 5.00 (n=3) | 11891.29 ms |
| LLM No Verifier v2 | 0.7826 | 0.8182 (n=22) | 6/22 | 0/19 | 4.32 (n=19) | 5207.65 ms |
| LLM Partial-pass v2 | 0.5217 | 0.9375 (n=16) | 0/16 | 5/19 | 3.73 (n=15) | 7607.35 ms |

### Q36：为什么 No Verifier Correctness 最高，却不是推荐方案？

它覆盖最积极，但 22 条实质答案中有 6 条被观察到不受直接证据支持的专业事实，4 道无答案题自动决策也全部误接受。它说明 LLM 能提高完整性和可读性，同时证明 Verifier 的安全价值。

### Q37：Strict 的 Faithfulness 1.0000，为什么不是最好？

因为只有 3 条实质答案进入 Faithfulness 分母，19 道可回答题中有 16 道过度拒答。高忠实度主要来自极低覆盖，必须与分母和 over-refusal 一起解释。

### Q38：Partial-pass 相比 Strict 改善了什么？

Over-refusal 从 16/19 降到 5/19，实质答案从 3 条增加到 16 条，同时 extension 中观察 hallucination 保持 0。它验证了 Claim-level 过滤能改善安全与覆盖折中。

### Q39：Partial-pass 是否优于 Rule Baseline？

不能这样说。Partial-pass 的 Faithfulness 0.9375 高于 Rule 的 0.8810，但 Correctness 0.5217 低于 Rule 的 0.5870，Over-refusal 也更高，延迟更大。四种方法没有单一全维度赢家。

### Q40：最大的错误类型是什么？

Strict 主要是过度拒答；No Verifier 主要是无答案误接受和证据不足推断；Partial-pass 仍会因属性存在性和 required-aspect 覆盖不足而误接受或漏答；Rule 容易返回相关但没有完全响应问题动作的事实。

## 8. 工程与性能

### Q41：为什么 LLM 延迟这么高？

这是单机本地 `qwen3:4b` 推理。Extension 中三个 LLM 方法平均约 5.21～11.89 秒；分阶段 trace 显示主要时间在模型生成，不在毫秒级检索、packing 或验证。

### Q42：做了哪些低风险延迟优化？

使用 Streamlit 启动预热、Ollama `keep_alive=30m`、Evidence Packer 上下文预算、最多 4 条 Claim、`num_predict=1536`、正常路径一次生成，以及只有 0 条 Claim 可保留时才重试。项目没有通过隐藏缓存伪装实时速度。

### Q43：143 项测试说明了什么？

说明配置、Schema、Retriever、Packer、Verifier、状态机、trace、实验合同、哈希和报告产物等工程合同通过回归。它不等于 143 道问答正确，也不能替代人工质量评测。

### Q44：系统完全离线吗？

核心问答可以离线运行：文档缓存、TF-IDF、NetworkX、Ollama 和规则 fallback 都在本机。打开官方 URL 或重新下载依赖和模型需要网络。

### Q45：如何启动项目？

```powershell
Set-Location E:\RAGagent
python scripts/smoke_llm_client.py --timeout 180
python -m streamlit run app/streamlit_app.py --server.port 8501
```

浏览器打开 `http://127.0.0.1:8501`。若 Ollama 不可用，可设置 `$env:AGENT_GENERATOR_BACKEND='offline_rule'` 后重启 Streamlit。

## 9. 局限与下一步

### Q46：当前最重要的不足是什么？

Partial-pass 仍有 5/19 over-refusal 和 2/4 无答案误接受；Correctness 未超过 Rule；本地 LLM 延迟为秒级；语料只有 6 页；extension 样本小；人工评分是单一用户确认；当前稀疏检索对同义改写的能力有限。

### Q47：下一步优先做什么？

第一是属性存在性验证，减少“实体存在但属性不在知识库”时的误接受；第二是 required-aspect 覆盖，改善多跳和双要求问题；第三是独立双人标注和一致性分析。之后才根据独立误差证据决定是否增加多语言 Dense Retriever。

### Q48：为什么现在不加 Dense Retriever？

Stage 8.5 剩余典型错误主要是语料缺失，不是正确 Chunk 没召回。现在加入 Dense 会改变冻结实验变量，却不一定解决主要问题。只有后续独立误差中至少约 30% 明确属于召回失败时，才值得重新评估。

### Q49：为什么不做多 Agent？

当前瓶颈是证据覆盖、验证边界和延迟，不是 Agent 数量。多 Agent 会增加调用成本、状态复杂度和归因困难，无法直接解决现有错误。

### Q50：项目能泛化到完整 scikit-learn 吗？

当前不能。架构可以扩展，但数据、图谱和实验结论只覆盖 6 个页面。扩展到完整 scikit-learn 需要重新建设知识库、审核关系、设计题集并独立评估。

## 10. 绝对不能混淆的口径

| 容易误述 | 正确说法 |

| “LLM Planner 已接入” | Planner 探针语义正确率 1/20，因此保持 Rule Router |
